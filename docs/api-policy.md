# API versioning and lifecycle policy

## Versioning

`/v1` is the canonical public API namespace. New integrations must use a
versioned path; endpoints and fields added to `/v1` are backward-compatible
additions unless documented otherwise.

The unversioned paths remain compatibility aliases for existing clients. They
return `Deprecation: true` and a `Link: </v1/...>; rel="successor-version"`
header on every response. They must not be used by new clients.

Breaking changes require a new major path version (for example, `/v2`). A
version is never changed in place by removing or renaming a response field,
changing a field's type or meaning, narrowing an accepted input, or changing
an endpoint's authorization, pagination, ordering, or error contract.

## Deprecation process

1. Document the replacement in the API reference, OpenAPI specification and
   `CHANGELOG.md` before or with the release that introduces it.
2. Mark the predecessor as deprecated in its OpenAPI operation and send the
   `Deprecation` and successor `Link` headers where applicable.
3. Give hosted API clients at least 90 calendar days' notice before removal;
   security, legal, privacy, or protocol-safety incidents may require a
   shorter window and will be explained in the advisory and changelog.
4. Announce the planned removal date in the changelog and release notes, then
   remove only in a subsequent major version.

The service remains read-only and must not add patient-identifying data during
a version transition. Amounts remain base-unit decimal strings: changing them
to JavaScript numbers is a breaking precision loss, not a formatting change.

## Changelog and OpenAPI contract

Every externally visible change belongs under `Unreleased` in
[`CHANGELOG.md`](../CHANGELOG.md), grouped as Added, Changed, Deprecated,
Fixed, Security, or Removed. The entry must say what a client needs to do and
identify any migration deadline.

[`openapi.json`](../openapi.json) is the reviewed API contract. CI compares it
with the specification generated by the live Fastify/Zod route schemas. For an
intentional API-spec change, run:

```sh
npm run openapi:update
```

Review and commit the resulting `openapi.json` alongside the route and
changelog changes. A failing OpenAPI contract test therefore means either an
uncommitted intended API change or an accidental one that needs review.
