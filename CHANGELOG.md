# Changelog

## Unreleased

### Added
- **Populated-data migration CI** (#277): the migrations job applies all but the newest migration to a clean Postgres database, inserts representative rows at that schema version, then deploys the remaining migration and checks the migrated records and final schema. This catches failures hidden by an empty database.

- **Amount columns land as NUMERIC on Postgres** (#273): `Voucher.amount/settledNet/settledFee`, `Receipt.amount`, `FaucetDrip.amount`, `Service.price` and `ServicePriceChange.price` become `NUMERIC(39,0)` (an i128 has at most 39 digits) through migration `20261119000001_amount_numeric_to_decimal`, moved out of `prisma/postgres-pending/` and tightened from plain `numeric`. The migration is forward-only and transactional: a preflight aborts it, changing nothing, if any stored value is not a plain decimal integer of at most 39 digits; each column uses an explicit `USING` cast, so values (the i128 maximum included) are preserved exactly; the text-regex `CHECK` constraints are re-created as `>= 0` under the same names. The committed schema stays SQLite/strings; columns marked `// pg:decimal` are rewritten to `Decimal @db.Decimal(39, 0)` by `scripts/use-postgres.sh`, which the CI `migrations` and Postgres test jobs already run. `src/db.ts` turns every `Decimal` read back into an exact string (`toFixed(0)`, never exponent notation), so every API response, the indexer, reconcile and snapshots still see decimal strings and no response changes shape. The rollback is in `docs/RUNBOOK.md` and the migration header. `src/__tests__/amount-numeric.test.ts` covers the conversion helper and, on Postgres, the column type and i128 round trip.
- **Keyset index for voucher lists filtered by clinic and status** (#274): composite index `Voucher(providerAddress, status, seq)` (migration `20261119000000_voucher_clinic_status_seq_index`, additive, rollback `DROP INDEX "Voucher_providerAddress_status_seq_idx"`). On Postgres with 200k vouchers across 20 clinics, `WHERE providerAddress = ? AND status = 'Settled' ORDER BY seq LIMIT 20` went from a bitmap scan of the clinic's 10 000 rows plus a top-N sort (6.6 ms) to an index scan that reads 21 rows (0.06 ms); `ORDER BY seq DESC` is a plain backward index scan. The route query is unchanged. The `migrations` CI job (drift check) passes locally against a fresh Postgres 16.
- **Prune old `ContractEvent` rows behind a setting** (#275): `EVENT_RETENTION_DAYS` (default `0` = keep forever, nothing is ever deleted unless it is a positive number) lets `pruneContractEvents` (`src/lib/retention.ts`) delete event-log rows older than the cutoff. Only events of vouchers in a final status (`Settled`, `Refunded`) and events with no voucher are eligible; history of open (and unknown) vouchers is left intact. Deletes run in bounded batches of 500, keyset-paged so kept rows are not re-read. It runs with the hourly retention pass in the indexer and from `src/scripts/cleanup-retention.ts`. No schema change. Tests in `src/__tests__/retention.test.ts`; README and `.env.example` document the setting.
- **Deterministic seed with `--seed` and `--size`** (#276): `npm run db:seed -- --seed <n> --size small|medium|large` seeds the PRNG that drives every address, id, amount and timestamp, so two runs with one seed write identical rows and another seed writes a different, equally repeatable dataset. Seed `0` (the default) reproduces the previous dataset exactly. Malformed flags are an error rather than a silent default. `src/__tests__/seed.test.ts` asserts identical rows for one seed, different rows for another, and the argument parser; `CONTRIBUTING.md` documents the flags.
- **`client.stream()` — the live voucher feed in the typed client** (#287): `@sci-healthcare/client` gains `stream(filters, handlers, options)`, which opens `GET /stream` and returns a handle whose `close()` stops reconnecting for good. It is built on `fetch`, not `EventSource`: the latter is absent on Node 22 and cannot carry the `Last-Event-ID` header, so the same code now runs in a browser and in Node. Exactly one of `voucher` or `provider` is required, checked client-side the way the route checks it. Drops reconnect with jittered exponential backoff (500 ms toward a 30 s ceiling) and stop retrying outright on a fatal 4xx/422 instead of hammering an endpoint that rejects the query; a connection that survives `stableAfterMs` (5 s) resets the attempt counter, so an hour-long outage ends in ~30-second retries rather than an ever-growing delay; and a stream that sees no heartbeat for 45 s is treated as dead and replaced, which catches a proxy that silently dropped the body. Each attempt gets its own `AbortController`, so cancelling a stalled read never closes the handle. **Known gap:** `src/routes/stream.ts` frames no SSE `id:` field, so `Last-Event-ID` is sent but the server cannot replay what was missed — re-read the JSON routes after `onReconnect` to be certain of current state. Tests in `src/__tests__/client-stream.test.ts` drive a real HTTP server and cover the backoff curve, jitter bounds, the storm reset, idle detection, and the fatal-status stop; the client README's "Live voucher stream" section documents the behaviour and the gap.
- **Email notifier example rewritten to the real webhook contract** (#292): `examples/email-notifier/` now checks a payload before it mails anything, in order: the raw-body HMAC-SHA256 signature in `x-sci-signature` (hex, or with the `sha256=` prefix other tooling adds, compared in constant time — a missing header or secret is a rejection, never a pass), a 64 KiB body cap answered `413` before parsing, the payload shape, then a privacy guard that refuses any payload carrying a beneficiary or patient field before a byte of mail is composed. The refusal returns a fixed message and logs the field path only, so the webhook response cannot be used to probe which patient a voucher belongs to. Templates are driven by the fields `src/lib/webhooks.ts` actually sends — `voucherId`, `status`, `event`, `ledger`, `txHash` — with one allow-listed facts array feeding both the text and the HTML body and every value escaped; the previous `amountDisplay` / `serviceLabel` fields were invented and silently rendered `undefined`. `nodemailer` is imported lazily inside the SMTP transport, so `npm test` in the folder and the repo's CI both run with nothing installed and the console transport stays the default. `npm --prefix examples/email-notifier test` runs 30 `node --test` cases; `src/__tests__/email-notifier.test.ts` covers the same server through vitest, because the CI `test` job never runs `node --test`. `eslint.config.js` lists Node globals for `examples/**/*.js` — the TypeScript examples never hit `no-undef`, since typescript-eslint switches it off for `.ts`, so this plain-JS example is the first to expose the gap.
- **Whether a claim carried a presence proof** (#318): `Voucher.claimedWithProof` records how a voucher was claimed. The `voucher_claimed` event is byte-identical for `claim` and `claim_with_proof`, so the indexer reads `get_voucher_options(voucher_id)` when it projects a claim and derives the flag from `presence_commitment`: a voucher funded with a commitment can only be claimed with the proof, and one funded without it can only be claimed without. `null` means "not known" — a claim whose options read failed, or a row written before this column existed — so absence is never reported as "no proof". The read happens once per voucher (a replayed claim, or a later status change on an already-answered row, asks no questions), it is skipped entirely when the indexer is built without a chain reader, and under `NODE_ENV=test` that reader is absent by default so the suite stays network-free like the startup contract validation. `readVoucherOptionsFromChain`/`hasPresenceProof` live in `src/stellar/reconcile.ts` beside the existing voucher read, and the `Option<Bytes<32>>` encoding was verified against real contract-scoped XDR rather than assumed. `GET /vouchers`, `GET /vouchers/:id` and `?fields=` expose the new key. Migration `20261118000001_voucher_claimed_with_proof`; `docs/data-dictionary.md` updated. Tests in `src/__tests__/indexer-projections.test.ts`, `src/__tests__/reconcile.test.ts`, `src/__tests__/sparse-fields.test.ts`.
- **Matching-funding desk: sponsor matches indexed and published** (#317): the indexer now reads the sponsor contract when `SPONSOR_CONTRACT_ID` is set, and the API says who funded a voucher's top-up. Three tables — `Sponsor` (terms + last reported balance), `SponsorBudgetEvent` (the audit trail, keyed by event id) and `SponsorMatch` (the sponsor's contribution, keyed by the voucher it funded and uniquely indexed by the voucher it was made against) — written from `budget_deposited`, `budget_withdrawn`, `rules_set`, `match_created`, `match_settled` and `match_refunded`. `available` is the balance the contract reported at the last movement, never a sum this backend keeps, because matching spends budget without emitting a budget event. `GET /sponsors` and `GET /sponsors/:address` serve the directory with per-sponsor totals; `GET /vouchers`, `GET /vouchers/:id` and `GET /vouchers/due` gain `matchedAmount`, `matchedAmountDisplay`, `matchedBy`, `matchStatus` and `matchedAt`, all `null` when nothing matched (a zero would be a different fact and could not be told apart afterwards), all built from one batched `sponsorMatch` lookup per page. The terms and the balance are `null`, not zero, for a sponsor seen for the first time by a match, so a start-ledger gap is visible instead of being smoothed over. `SPONSOR_CONTRACT_ID` is optional: unset, the routes answer an empty directory rather than `503`. Migration `20261118000002_sponsor_matches`. Two things are deliberately not in scope and are worth saying so: `/stats` gains no sponsor counters (it is a protocol-wide dashboard and a sponsor total is a directory-wide scan), and `verifyReferentialIntegrity` does not treat a match as a foreign key to check, because the desk's `matched_voucher_id` is a voucher the funder never issued and the original may legitimately predate the cursor. Decoder fixtures for the six events are recorded as blocked in `src/__tests__/decoder-fixtures.test.ts` rather than invented: `contracts/sponsor` has no deployment id anywhere in this repo (not in `README.md`, `.env.example` or `docker-compose.yml`), so there is nothing to capture from. Tests in `src/__tests__/sponsors.test.ts` (including a query-count check that a seven-row page costs the same Prisma operations as a one-row page), `indexer-projections.test.ts`, `idempotency.test.ts` (the sponsor events are in the whole-table replay snapshot), `sparse-fields.test.ts`. README, `docs/data-dictionary.md`, `docs/RUNBOOK.md` and `openapi.json` updated.
- **Chaos test for RPC failover** (#307): `src/__tests__/rpc-failover-chaos.test.ts` replays the recorded fixtures through two fake endpoints behind a real `RpcPool`, drawing every call from a seeded generator — transport error, timeout, a replica that is behind, healthy — with the first cursor continuation forced to fail so no seed can pass by never handing a read over. Six seeds; each one asserts the read model after convergence equals the same log read through one healthy endpoint, that the cursor lands exactly on the tip, that failover actually engaged, and that a replay of the seed costs the same polls and leaves the same database. `src/__tests__/paging.test.ts` pins the rule the run discovered. Two things are out of scope and said so in the file: a server whose `latestLedger` runs ahead of the events it returns cannot be told apart from an honest one by anything inside a single `getEvents` response, and a replica that re-serves events from below the cursor is not what Soroban's server-side `startLedger` filter produces.
- **The test suite runs in three time zones** (#306): CI covered UTC only, so a day boundary that drifted once the service ran somewhere else was invisible until it was reported from the field. The `test` job's matrix gains a `tz` axis — `UTC`, `Africa/Lagos` (UTC+1 all year, which is where this backend is deployed) and `Pacific/Kiritimati` (UTC+14, the furthest ahead of UTC there is, so an instant late on one UTC day is already the next day there) — and the job sets `TZ: ${{ matrix.tz }}`. The job is now named `test (<engine>, <tz>)`: GitHub reports checks by name, so four entries under the old engine-only name would have had Lagos silently replaced by Kiritimati in the pull request. The zone axis runs on SQLite only — every day boundary here is JavaScript date arithmetic (`utcDateString` is `toISOString().slice(0, 10)`, the `/stats/daily` window anchors on `Date.UTC(now.getUTCFullYear(), now.getUTCMonth(), now.getUTCDate())`, and `createdFrom`/`createdTo` are `z.string().datetime({ offset: true })`, which normalises an offset to an instant rather than reading it as a day), no query in this service derives a day in SQL, and Prisma stores instants — so the engine axis would add nothing the zone axis could not catch. One product change lands: `utcDateString` answered a date *string* by taking its first ten characters, so `'2026-10-02T02:00:00+05:00'` bucketed onto the 2nd when its UTC day is the 1st; it now parses the instant first, which is what its name and the `date` key of `/stats/daily` promise. Every production caller already passed a `Date` — the indexer's timestamps come from `asTimestamp` — so no indexed row moves. `src/__tests__/stats-perf-latency.test.ts` loops four zones inside the process — the matrix's three plus `America/New_York` — which is what lets it fail on a UTC runner too, and pins which day an instant is billed to through `recordDailyStatFunded`/`Settled`/`Refunded`, the days a `backfillDailyStats` run produces, and the three days `/stats/daily` returns for a fixed clock. The extra zone is not decoration: UTC midnight plus a *positive* offset is still the same calendar date, so Lagos and Kiritimati together cannot see a window labelled from local fields, and only a zone west of UTC can. `src/__tests__/ci-workflows.test.ts` pins the matrix entries, the `TZ` wiring and the per-entry name. Mutation-checked: `utcDateString` reading `getFullYear()`/`getMonth()`/`getDate()`, `utcDateString` answering a string with its own first ten characters, the `/stats/daily` anchor using local getters, its day labeller doing the same, and a `name:` that drops the zone — all five turn red on exactly the tests that should and go green again on revert, with the ambient zone at UTC as well as in Lagos.
- **Clinic capacity and current exposure** (#316): the registry's `set_capacity` emits `capacity_changed` (topic `provider`, data `max_outstanding`, where `0` means unlimited); the indexer now projects it onto `Provider.capacity`, so a clinic's voucher cap survives a restart instead of living only on chain. `GET /providers` and `GET /providers/:address` expose `capacity` (the indexed cap, `null` until the registry first sets it) alongside `openVouchers` — the live count of that clinic's `Funded` and `Claimed` vouchers — so a funder can see a clinic is at capacity before the transaction reverts with `ProviderAtCapacity`. `openVouchers` is one grouped `count` per page, never one per row. Adds the nullable `capacity` column (migration `20261118000000_provider_capacity`); `docs/data-dictionary.md` and the decoder fixture coverage updated to match. No breaking change to existing response fields.

- **Self-hosting on one VPS** (#300): `deployments/docker-compose.prod.yml` runs Postgres, a one-shot `npx prisma migrate deploy` job, the API and Caddy on a single server, and `docs/self-hosting.md` is the guide that goes with it — DNS before the first boot, the firewall, the env file, the ledger you start at, backups (and the restore that proves a backup is one), the upgrade order that migrates before the new code serves, and a rollback with a commit to go back to. The dev stack's `prisma db push` is replaced by the reviewed migrations in `prisma/migrations`, and the three database credentials are assembled once, in the `x-database-url` anchor, so the API, the migration job and the Postgres container cannot drift apart. Only 80 and 443 are published, and the API's absence from that list is load-bearing: the app sets `trustProxy: true` and reads the client address from `X-Forwarded-For`, so a container reachable directly on 8080 is a service where any client can name any IP and walk past the per-IP rate limits. `ops/Caddyfile` deliberately adds no `encode` and no security headers, because `@fastify/compress` and `@fastify/helmet` already do both. `.env.prod.example` is the committed template and keeps every secret and every operator-specific value blank; the `.env` it seeds is gitignored. Configuration is tested structurally: `src/__tests__/self-hosting.test.ts` reads the compose file, the template, `.gitignore`, the Caddyfile and the guide, and asserts each invariant the guide claims — every interpolated name is defined, every name the stack sets is one `src/env.ts` declares, every required one is supplied, nothing but Caddy publishes a port, and every section link points at a heading that exists. No runtime, schema or API change.
- **Docs link checking in CI** (#301): `.github/workflows/links.yml` runs [lychee](https://github.com/lycheeverse/lychee) over every tracked Markdown file on a pull request that touches one, weekly on `main`, and on dispatch. Two steps, two severities: a link to a file or a section inside this repository that no longer resolves fails the job, because only the author could have broken it and only the author can fix it, while a link somewhere else on the internet is retried and posted to the run summary without blocking the merge, because a third-party page moving — or the free-tier API in the README still being asleep — is not a reason to hold a PR. The binary comes from an exact release tag and is verified against its published sha256 before it runs, the way `security.yml` pins its tools, with `permissions: contents: read` and `persist-credentials: false`. `lychee.toml` holds the shared settings, so `lychee --config lychee.toml --scheme file $(git ls-files '*.md')` reproduces the fatal half before pushing. The check found one real breakage on `main`: the README's `docs/banner.png` was never committed and rendered as a broken image, so that block is gone. Tests in `src/__tests__/ci-workflows.test.ts` pin the triggers, the least-privilege permissions, the pinned download with its checksum, exactly one `continue-on-error` step, and the settings that make external flakiness non-fatal.
- **Type-check every TypeScript project the CI was not reading** (#312): `npm run typecheck` now runs four configs — the server, a new `tsconfig.tooling.json` for `scripts/` and `test/`, `packages/client`, and `examples/telegram-bot` — all extending `tsconfig.base.json`, which holds `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `exactOptionalPropertyTypes` and `moduleResolution: bundler`. Path-bearing options (`outDir`, `rootDir`, `include`) stay in the leaves because `extends` resolves them relative to the base file, and an inherited `outDir: dist` would emit a tooling check into the server's build directory. Nothing here uses project references: every config is checked with `--noEmit`, so the gate stays independent of the build. The errors the new projects found are fixed at their source — `scripts/generate-client.ts` read `spec.openapi` off a type that omits it, `examples/telegram-bot/src/index.ts` re-exported a `./email.js` module that does not exist, so that example's entry point has never loaded — rather than silenced, and `test/integration/quickstart.test.ts` is excluded because it is an orphan that has never compiled (it imports `../app.js`, a path that only resolves from inside `src/`, and no vitest include pattern or workflow loads it; reported, not deleted). `src/__tests__/tsconfig-projects.test.ts` pins the project set, each config's include globs, and the strict flags per project, so a directory cannot quietly fall out of the gate again.
- **Async iterators over paginated client lists** (#286): `client.vouchersIterate()`, `client.providersIterate()` and `client.receiptsIterate()` are async generators that follow `nextCursor` for you, and `client.servicesIterate()` walks the single-page catalogue. - **405 for a known path called with the wrong verb** (#126): the API is read-only, but a `POST` to `/vouchers` answered `404`, which reads to an integrator as "this endpoint does not exist" when it is their method that is wrong. - **Embedded related records on the voucher routes** (#167): `GET /vouchers` and `GET /vouchers/:id` accept `?include=receipt,provider`, so a voucher page can render the receipt and the clinic without a second request per row. `receipt` is the exact object `GET /receipts/:voucherId` serves (`null` for a voucher that has not settled) — on `GET /vouchers/:id`, which already carries the stored receipt row, asking for it returns this canonical shape instead of the raw row. `provider` is the exact object `GET /providers/:address` serves (`status`, `registeredAt`, cached `metadata` and the full service catalogue) in place of the `address`/`name`/`country` summary; without the parameter both routes respond exactly as before. ### Added
- **Indexer backoff on RPC errors**: a failed cycle now doubles the wait before the next one (`nextDelay`, exponential from `INDEXER_POLL_MS` with 25% jitter, capped by the new `INDEXER_BACKOFF_MAX_MS`, default 60s) and resets on the first cycle that works. The failure is logged once per streak instead of once per attempt, with a matching `indexer recovered` line carrying the attempt count.
- **RPC failover**: `SOROBAN_RPC_URLS` takes a comma-separated list of endpoints; `SOROBAN_RPC_URL` still works and is used when the list is unset. After `SOROBAN_RPC_MAX_FAILURES` consecutive failures (default 3) reads move to the next endpoint and the switch is logged. `/version` reports every configured endpoint and `/ready` reports the active one as `checks.rpcUrl`, both redacted.
- **Reconciliation against the chain**: `npm run indexer:reconcile [-- --fix] [-- --sample <n>]` compares every non-terminal voucher (plus a rolling sample of terminal ones, default 25) with `get_voucher` through simulation. Differences are recorded in the new `ReconcileMismatch` table and exposed on `/ready` as `checks.reconcileMismatches` and `checks.reconcile`. Drift is reported but does not make `/ready` 503: unlike a failed event it says nothing about whether the instance can serve traffic. `--fix` rewrites the differing rows from chain state; the command exits non-zero while any mismatch is open. See `docs/RUNBOOK.md`.
- **Faucet drip counts**: with the optional `FAUCET_CONTRACT_ID` set, the indexer subscribes to the testnet faucet and projects its `dripped` events into the new `FaucetDrip` table (keyed by on-chain event id, so replay cannot inflate the count). `/stats` gains `faucetDrips` and `faucetWallets` (distinct wallets), both `0` when no faucet is configured.
- **Prometheus metrics**: `/metrics` serves Prometheus text with default process metrics, `indexer_lag_ledgers`, `indexer_seconds_since_success`, `events_applied_total{name}`, `events_skipped_total{name}`, and `http_requests_total` / `http_request_duration_seconds` labelled by route pattern. It is exempt from the public rate limit. Indexer series are populated in the process that runs the indexer (combined mode or the worker).
- **Dead-lettered events**: an event that fails to project is stored in the new `FailedEvent` table (id, name, ledger, raw XDR, error, attempts, first/last seen) instead of only being logged. `/ready` reports degraded while any exist (`checks.failedEvents`). `npm run indexer:retry-failed` re-decodes and re-applies them, deleting rows that succeed. The table is created by the `20260102000000_failed_events` migration.

### Fixed
- **A failover onto a lagging RPC endpoint re-applied events** (#307): `collectEvents` took `throughLedger` from whichever page ended the range, and a mid-read failover hands that page to a replica that has not indexed the ledgers the earlier pages already returned. Its `latestLedger` sits behind events already in the result, so the cursor the indexer committed did not cover them — they were applied, then applied again on the next poll. `DailyStat` counters, which are summed per event, and the webhook outbox, which is written per projection, each recorded the fact twice; `ContractEvent` hid it because it is keyed by the on-chain event id. Events past the ledger the cursor reports are now held back for a cycle whose cursor reaches them, and `hasMore` says the range was left unfinished. Found by the chaos test, not by hand.
- **Voucher id ordering** (#61): `Voucher.id` is the on-chain u64 kept as a string, so every `ORDER BY id` was lexicographic and put voucher 10 before voucher 9. `Voucher` now carries a numeric `seq` mirror of the id, written from the id by the `voucher_created` handler (`voucherSeq()` in `src/lib/voucher_seq.ts`) and backfilled for existing rows by migration `20260106000000_voucher_seq`; `GET /vouchers` (both the sorted page and the keyset cursor), `GET /vouchers.csv` and the amount-filtered page all sort by `seq`, with `id` kept as the final tie-break. `seq` is `BIGINT` rather than `Int` because the seeded id space starts at 9e12, and it is null for a hand-written id that has no numeric value (`bulk-0001`), which then sorts last in both directions so no row can fall between two pages. No response gained a field. Tests in `src/__tests__/voucher_seq.test.ts`.
- **tests:** vitest now collects only `src/**/*.test.ts`. The `node:test` suite at `.github/scripts/automerge.test.cjs` has its own CI job, but was also being collected by vitest and failed `npm test` as "no test suite found".
